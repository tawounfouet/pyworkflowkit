# PyWorkflowKit 0.8.0a1

Development milestone: M47 — External Workload Interoperability Contract

## Capability

0.8.0a1 introduces External Workload Contract v1, the first ecosystem interoperability
contract built on top of the stable 0.7 runtime.

The contract treats one execution owned by another runtime as one atomic PyWorkflowKit
task while keeping foreign runtime semantics outside the core.

## Added

- `EXTERNAL_WORKLOAD_CONTRACT_VERSION = "1"`;
- `ExternalWorkload` protocol;
- immutable `ExternalWorkloadResult`;
- `ExternalRetryOwner`;
- `ExternalWorkloadAdapter`;
- `external_workload_task()`;
- `ExternalWorkloadError`;
- `ExternalWorkloadRetryOwnershipError`;
- dedicated public import surface under `pyworkflowkit.integrations`;
- M47 unit and reference acceptance coverage.

## Result normalization

Successful external executions become:

~~~text
ExternalWorkloadResult
        ↓
TaskResult
├── output
├── ArtifactReference[]
└── ExternalRunRef
~~~

Foreign execution identifiers remain foreign and are recorded through
`ExternalRunRef`.

## Failure normalization

Foreign exceptions and failed normalized results cross the integration boundary through
`ExternalWorkloadError`.

The trusted-Python executor maps the boundary failure into the existing
`TaskExecutionError` while preserving the foreign normalized `error_category`.

This allows ordinary `RetryPolicy.retryable_error_categories` to work across the
external workload boundary.

## Retry ownership

Exactly one runtime owns retry:

~~~text
pyworkflowkit
or
external
~~~

External-owned retry requires PyWorkflowKit `max_attempts=1`.

## Timeout and cancellation

M47 adds no competing timeout/cancellation lifecycle.

External workload tasks continue to use the existing TaskDefinition/Executor timeout and
cancellation capability model.

## Compatibility

The stable 0.7 package-root API is unchanged.

The existing PyIngestKit adapter remains supported and its acceptance suite continues to
define backward compatibility.

## Boundaries

M47 adds no scheduler, polling daemon, HTTP dependency, remote cancellation protocol,
cloud SDK, provider registry or business-specific TaskType.
