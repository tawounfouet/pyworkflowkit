# PyWorkflowKit 0.5.0a5

Development milestone: M36 — Security Hardening

## Capability

PyWorkflowKit 0.5.0a5 closes the functional 0.5.x roadmap with explicit subprocess,
observability, and supply-chain security guardrails.

## Added

- SubprocessSecurityPolicy;
- executable allowlists;
- working-directory root restrictions;
- environment-key restrictions;
- configurable environment inheritance;
- stdin/stdout/stderr boundary limits;
- SubprocessSecurityError;
- ObservabilitySecurityPolicy;
- recursive RuntimeEvent payload redaction for external sinks;
- default sink-error-message redaction;
- Bandit CI gate;
- pip-audit CI gate;
- detect-secrets CI gate;
- pull-request dependency review integration, with full enforcement when GitHub Dependency Graph is enabled;
- M36 unit and reference acceptance coverage.

## Changed

SubprocessExecutor no longer inherits the parent process environment by default.

This is an intentional security hardening change on the pre-stable 0.5.x line.

## Default subprocess limits

```text
inherit_environment = false
max_stdin_bytes      = 1 MiB
max_stdout_bytes     = 10 MiB
max_stderr_bytes     = 10 MiB
```

Executable, cwd, and environment allowlists remain opt-in because PyWorkflowKit is a
generic embedded runtime.

## Observability

Durable RuntimeEvents are unchanged.

External RuntimeEventSink plugins receive a redacted projection by default.

```text
durable event
    ↓
security projection
    ↓
external telemetry
```

## Security category

Subprocess policy violations use:

```text
error_type     = SubprocessSecurityError
error_category = security_policy
```

Retry behavior remains owned by RetryPolicy + RetryEngine.

## Trust boundary

0.5.0a5 does not make PyWorkflowKit a sandbox.

Local handlers and installed plugins remain trusted Python code.

ProcessExecutor provides process isolation but not an adversarial security boundary.

SubprocessExecutor provides shell-free execution plus policy checks but not OS sandboxing
or resource containment.
