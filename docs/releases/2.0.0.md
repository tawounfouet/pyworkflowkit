## Stable acceptance

PyWorkflowKit 2.0.0 is accepted only while all roadmap criteria remain true:

1. `WorkflowDefinition` is the canonical authoring root.
2. `TaskDefinition` represents one workload boundary.
3. `ExecutionPlan` is deterministic and public.
4. Graph implementation internals remain internal.
5. Workflow/task/attempt identifiers remain distinct.
6. Retry creates a new `TaskAttempt`.
7. Timeout and cancellation preserve uncertainty.
8. `ExternalRunRef` remains durable and portable.
9. Recovery preserves identities and reconciles before rerun.
10. Durable outputs remain portable and bounded.
11. `InlineExecutor` remains fully qualified.
12. SQLite durable recovery remains qualified.
13. Optional executors declare capabilities explicitly.
14. Metadata transitions remain protected.
15. Serialization remains versioned and non-executable.
16. Plugins require explicit activation.
17. Sibling integrations remain optional and opaque.
18. Customer 360 workflow/recovery qualification passes.
19. Clean wheel/sdist artifacts install on supported Python versions.
20. No release blocker remains.

```text

ProcessExecutor      explicit process boundary

```

Capability declarations, timeout semantics, cancellation semantics, serialization

## Sibling integrations

PyIngestKit and PyTransformKit remain optional sibling frameworks.

PyWorkflowKit 2.0 does not add hard runtime dependencies on either sibling package.
Integration adapters retain opaque workload/resource boundaries, credential references,
explicit retry ownership, and reconciliation for unknown external outcomes.

The stable compatibility promise is contract-based rather than an implicit package import
range: sibling packages are qualified through independently packaged integration fixtures
and may evolve independently while preserving the frozen adapter contracts.
