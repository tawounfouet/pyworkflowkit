# PyWorkflowKit 0.6.0a4

Development milestone: M40 — Non-blocking Retry

## Capability

`0.6.0a4` replaces blocking retry backoff in the concurrent/long-lived runtime with explicit durable retry eligibility.

```text
retry_eligible_at = failed_at + delay_seconds
```

## Added

- `TaskAttempt.retry_eligible_at`;
- `RunStateMachine.schedule_retry()`;
- durable retry eligibility serialization and persistence;
- Alembic revision `0003_retry_eligible_at`;
- retry-wait diagnostics in `RecoveryAssessment`;
- durable SQLite retry-wait restart acceptance.

## Concurrent behavior

`ConcurrentRunner` no longer calls `Sleeper.sleep()` for retry delays. Pending retries are coordinated through local monotonic deadlines while portable wall-clock eligibility is persisted on the failed attempt. Other READY work can continue during backoff. Timeout retries use the same mechanism.

## Sequential behavior

The sequential `Runner` keeps blocking `Sleeper` behavior but persists retry eligibility first, so a crash during backoff remains recoverable.

## Recovery

A retry-waiting TaskRun is explicit runtime evidence, not ambiguous RUNNING work. Before eligibility it remains ACTIVE; once overdue and stale it becomes resume-eligible without external reconciliation. M39 then creates Attempt N+1 on the same TaskRun.

## Persistence

SQLite and PostgreSQL migration qualification advances to `0003_retry_eligible_at`.

## Compatibility

Lifecycle enum sets, RuntimeEvent taxonomy, RunManifest schema version 1, Plugin API version 1, RetryPolicy, RetryEngine ownership, and Executor capability contracts remain unchanged.

## Roadmap

M40 completes the functional M37–M40 scope of 0.6.x. Next: transverse qualification and promotion to `0.6.0` stable.
