# PyWorkflowKit 2.1.1

> **Release type**: stable patch remediation  
> **Release line**: 2.1.x  
> **Historical qualified tag**: `v2.1.0` → `f5fc4c8a8f258536c0d49e6f11d27ada406c9a61`  
> **Remediated main baseline**: `2bbbc50b9f348bbb6a0c614af1893cc2bc0415fc`  
> **Date**: 2026-10-04

PyWorkflowKit 2.1.1 is the patch release used to publish the 2.1 line after the
post-`v2.1.0` release audit. The existing `v2.1.0` tag is deliberately preserved and
is not moved or rewritten.

This patch changes release documentation, evidence, qualification guards, publishing
hardening, and one stale package-root docstring. It does **not** change runtime behavior,
public workflow contracts, persistence schemas, state-machine semantics, executor
semantics, or the frozen CLI machine contract.

---

## Why 2.1.1 instead of moving v2.1.0?

The audit found that the `v2.1.0` Git tag was technically qualified, but its surrounding
release metadata and publication state were not fully reconciled:

- the README still announced 2.0.0;
- the primary README quickstart did not match the actual `InlineExecutor` handler
  contract;
- the SQLite README constructor keyword was wrong;
- `SECURITY.md` still described 0.5.x as the current stable line;
- release notes contained stale test/check counts and unsupported multi-OS claims;
- the frozen CLI command list was documented incorrectly;
- GitHub Release and PyPI publication were not actually complete;
- `main` release workflows still used several mutable action references.

Because `v2.1.0` is already a public Git identity, 2.1.1 preserves tag immutability
instead of repointing that tag.

---

## Remediation included

### Documentation correctness

- README status aligned with the 2.1 stable line.
- Root public API documentation aligned with `pyworkflowkit.__all__`.
- Quickstart dependencies now use
  `TaskExecutionContext.dependency_outputs`.
- SQLite example now uses `SQLiteMetadataStore(path=...)`.
- Security support policy updated to the maintained 2.x lines.
- Release notes and roadmap now distinguish a qualified tag from an externally
  published release.
- Duplicate `2.1.0rc1` changelog metadata removed.
- Package-root docstring changed from the stale “2.0 stable root API” wording to
  “stable V2 root API”.

### Executable release evidence

- Machine-readable `contracts/release_evidence_v2_1.json`.
- CI guard that executes the primary README quickstart directly from Markdown.
- Drift guards for version, CLI command contract, release metrics, and operational docs.

### Publishing and supply-chain hardening

- Portable, self-verifying `SHA256SUMS`.
- PyPI publication restricted to `vX.Y.Z` tags.
- Git tag version must equal `pyproject.toml` version.
- The exact release SHA must already have a successful Release Qualification run.
- Release-critical GitHub Actions are pinned to immutable commit SHAs.
- `uv` is pinned instead of using `latest`.

## Publication gate

A tag is not sufficient evidence of publication.

LOT-38 closes only after all of the following are true:

1. `v2.1.1` points to the fully qualified release commit.
2. Release Qualification succeeds on that exact tag SHA.
3. GitHub Release `v2.1.1` is published.
4. Trusted Publishing publishes `pyworkflowkit==2.1.1` to PyPI.
5. Wheel, sdist, SBOM, checksums, and provenance are available.
6. A clean environment installs `pyworkflowkit==2.1.1` from PyPI.
7. The canonical import / CLI / README smoke path passes outside the source checkout.

```bash
pip install "pyworkflowkit[otel]==2.1.1"
```

## Upgrade from 2.1.0

No database migration or runtime migration is required solely for this patch.

```bash
pip install --upgrade pyworkflowkit==2.1.1
```

The upgrade primarily provides corrected package documentation and hardened release
engineering around the same 2.1 runtime contract family.
