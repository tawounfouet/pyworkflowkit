# PyWorkflowKit 0.5.0a2

Development milestone: M33 — AsyncExecutor

## Capability

PyWorkflowKit 0.5.0a2 adds explicit asyncio workload execution with cooperative
cancellation while preserving the coordinator-owned runtime state model introduced in
0.4 and extended by ProcessExecutor in 0.5.0a1.

## Added

- explicit async executor port;
- async handler type aliases;
- `ExecutorCapabilities.supports_async`;
- concrete `AsyncExecutor`;
- dedicated asyncio event loop and loop thread;
- native `execute_async()`;
- synchronous compatibility bridge for the historical Executor port;
- bounded active async capacity;
- per-handle asyncio.Task tracking;
- cooperative cancellation through `Task.cancel()`;
- ConcurrentRunner integration for cooperative executor cancellation;
- async soft-timeout acceptance through the existing timeout/retry model;
- M33 unit and reference acceptance coverage.

## Cancellation semantics

M33 distinguishes physical cancellation strength:

```text
ThreadExecutor
    cancellation = none

AsyncExecutor
    cancellation = cooperative

ProcessExecutor
    cancellation = hard
```

A cooperative async cancellation is considered successful only when the executor accepts
a cancellation request for a still-active task. ConcurrentRunner then owns the
TaskAttempt/TaskRun transition to CANCELLED after completion evidence is drained.

## Timeout semantics

AsyncExecutor declares SOFT timeout capability.

M33 does not claim that `asyncio.Task.cancel()` is hard termination. Timeout remains a
logical failed attempt represented by `ExecutionTimeoutError`.

## Compatibility

M33 intentionally leaves these contracts unchanged:

- package-root API;
- WorkflowRun / TaskRun / TaskAttempt status enums;
- RuntimeEvent taxonomy;
- RunManifest schema;
- MetadataStore schema and Alembic baseline;
- ThreadExecutor behavior;
- ProcessExecutor hard timeout/cancellation behavior;
- LocalExecutor behavior.

The only capability extension is the backward-compatible
`ExecutorCapabilities.supports_async=False` field.
