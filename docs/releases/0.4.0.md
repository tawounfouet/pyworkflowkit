# PyWorkflowKit 0.4.0

Release date: 2026-09-26

## Capability

PyWorkflowKit 0.4.0 adds bounded concurrent workflow execution with explicit
cancellation and timeout semantics.

This release closes milestones M25 through M31 on top of the local developer framework
qualified in 0.3.0.

## Highlights

- Explicit `ExecutorCapabilities` for parallelism, timeout, cancellation, and
  `max_concurrency`.
- Thread-safe `CapacityManager` with global and per-executor slot accounting.
- Immutable execution handles and a thread-safe completion queue.
- `ThreadExecutor` backed by Python's `ThreadPoolExecutor`.
- `ConcurrentRunner` with serialized coordinator-owned runtime state transitions.
- Parallel fan-out / fan-in execution with duplicate-ready protection.
- FAIL_FAST semantics that stop new dispatch while allowing already-running siblings to
  finish naturally.
- Thread-safe workflow cancellation requests with graceful draining of running work.
- `KeyboardInterrupt` normalized into the same graceful cancellation path.
- `TimeoutMode.NONE`, `SOFT`, and `HARD`.
- Backward-compatible `timeout_seconds` normalization to `SOFT`.
- Executor timeout-capability validation before run creation.
- `ExecutionTimeoutError` normalized through the existing retry engine.
- Late soft-timeout completions cannot overwrite the already-recorded timeout result.

## Execution model

The central concurrency rule is:

```text
workers execute workloads
        ↓
AttemptCompletion
        ↓
CompletionQueue
        ↓
ConcurrentRunner coordinator
        ↓
runtime state transitions
```

Workers never own WorkflowRun, TaskRun, or TaskAttempt transitions.

Capacity is bounded before dispatch:

```text
global limit
    +
executor max_concurrency
    +
optional executor-level limit
        ↓
effective dispatch capacity
```

## Cancellation semantics

Cancellation is capability-aware.

For `ThreadExecutor`, cancellation capability remains `NONE`. Therefore an explicit
workflow cancellation:

1. stops new initial-attempt and retry dispatch;
2. normalizes PENDING / READY work to CANCELLED;
3. allows already-running Python threads to finish naturally;
4. persists their actual terminal result;
5. finalizes the WorkflowRun as CANCELLED.

PyWorkflowKit 0.4.0 does not pretend that Python threads support safe hard termination.

## Timeout semantics

`ThreadExecutor` supports `SOFT` timeout semantics.

A soft timeout means:

```text
logical TaskAttempt
RUNNING
   ↓ deadline
FAILED
error_type     = ExecutionTimeoutError
error_category = timeout
   ↓
RetryEngine
```

The physical Python thread may continue after the logical timeout. Its late completion
is ignored for runtime state, while its capacity lease remains held until the thread
actually returns.

`HARD` timeout semantics are defined and validated but are not implemented by
`ThreadExecutor`. A hard timeout request is rejected before run creation.

## Public API freeze

The package-root API remains intentionally small.

0.4.0 adds `TimeoutMode` to the 0.3 public surface. Advanced concurrency components
remain available through their dedicated modules:

```python
from pyworkflowkit import TimeoutMode
from pyworkflowkit.adapters.executors.thread import ThreadExecutor
from pyworkflowkit.application.cancellation import CancellationController
from pyworkflowkit.application.concurrent_runner import ConcurrentRunner
```

This is intentional: the package root is not expanded into a general service locator or
an exhaustive export surface.

## Contract freeze

0.4.0 does not introduce incompatible changes to the existing stable evidence and
persistence contracts:

- RunManifest schema/version remains unchanged;
- runtime event model remains unchanged;
- metadata schema remains on the existing Alembic baseline;
- existing serialized TaskDefinition payloads that use `timeout_seconds` without
  `timeout_mode` remain valid and normalize to SOFT;
- the 0.3 public local/sequential workflow path remains valid.

No `TIMED_OUT` runtime status is introduced. Timeout remains a failed attempt with
explicit timeout error evidence.

The 0.4.0 release gate requires:

- Ruff lint and format checks;
- strict mypy over `src`;
- pytest with branch coverage >= 90%;
- Python 3.11, 3.12, and 3.13 matrices;
- wheel build and isolated installation smoke;
- exact package / public `__version__` / CLI version consistency at `0.4.0`;
- reference acceptance workflows;
- concurrent fan-out / fan-in acceptance;
- capacity and duplicate-ready race coverage;
- cancellation and KeyboardInterrupt coverage;
- timeout failure and retry coverage;
- PostgreSQL persistence and migration contracts;
- migration resources present in the installed wheel.

## Known limitations

0.4.0 does not provide:

- hard termination of Python threads;
- process isolation;
- async executor support;
- subprocess executor support;
- non-blocking retry backoff;
- crash recovery / resume / reconciliation;
- scheduler or future-run ownership;
- distributed worker infrastructure.

These limitations are deliberate product boundaries rather than hidden fallback
behavior.

## Architectural boundaries

PyWorkflowKit remains an embedded workflow runtime. It does not become:

- a scheduler;
- a web control plane;
- a worker-cluster platform;
- an IAM / RBAC system;
- a secret manager;
- an ingestion framework.

PyIngestKit remains an optional atomic workload integration.
