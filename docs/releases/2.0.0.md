# PyWorkflowKit 2.0.0

Stable V2 embedded workflow-runtime release.

## Status

```text
PyWorkflowKit 2.0.0
        ↓
Stable V2 architecture
Stable execution identity
Stable state / retry / timeout semantics
Stable Executor / MetadataStore boundaries
Stable versioned wire contracts
Stable optional sibling integration boundaries
```

PyWorkflowKit 2.0.0 is promoted from the fully qualified `2.0.0rc1` candidate.

No new runtime capability is introduced by the stable promotion.

## Promotion policy

```text
2.0.0rc1 qualified implementation
        ↓
version metadata
release metadata
stable classifier
stable evidence manifest
        ↓
2.0.0
```

The promotion policy is:

```text
same-qualified-implementation-version-metadata-only
```

Any architecture redesign or new runtime capability would require a new pre-release cycle
rather than being folded into this stable promotion.

## Stable execution model

PyWorkflowKit 2.0 freezes the distinction between:

```text
WorkflowDefinition
ExecutionPlan
WorkflowRun
TaskRun
TaskAttempt
```

Execution identifiers remain distinct:

```text
WorkflowRunId
TaskRunId
TaskAttemptId
CorrelationId
```

Every workload retry creates a new `TaskAttempt`. Timeout, cancellation and external
provider ambiguity preserve outcome uncertainty rather than inventing success/failure.

## Persistence and recovery

Stable persistence includes:

- InMemory metadata store;
- SQLite durable metadata store;
- PostgreSQL durable metadata store;
- protected state transitions;
- portable task-output checkpoints;
- external-run references;
- runtime events and lineage;
- recovery/reconciliation before ambiguous rerun.

Stable migration head:

```text
0005_v2_task_output_checkpoints
```

## Serialization

V2 wire contracts are:

- versioned;
- strict;
- canonical JSON;
- non-executable during deserialization;
- bounded by payload/depth limits;
- fail-closed on duplicate keys and non-finite numbers.

## Plugins and sibling integrations

Plugins require explicit activation.

PyIngestKit and PyTransformKit remain optional siblings. Core PyWorkflowKit does not import
them as mandatory dependencies.

Stable integration-contract versions:

```text
PyIngestKit     1
PyTransformKit  1
```

Raw credentials are not accepted across sibling boundaries. Unknown external outcomes
require reconciliation.

## Migration

The canonical migration guide is:

```text
docs/migration/V1_TO_V2.md
```

Migration is explicit, V1→V2 only, and fail-closed where semantic ownership cannot be
proven.

## Non-goals

PyWorkflowKit 2.0 does not require a cron scheduler, central scheduler server, distributed
worker fleet, message broker, web UI, multi-tenant SaaS control plane, enterprise RBAC
platform, ingestion engine, transformation engine or data catalog.

Those concerns remain external or optional layers.

## After 2.0

Maintenance releases in the `2.0.x` line must preserve the frozen V2 contracts.

New architectural capability belongs to a later roadmap and must not be retrofitted into
the 2.0 stable line.
