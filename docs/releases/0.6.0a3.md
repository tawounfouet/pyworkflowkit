# PyWorkflowKit 0.6.0a3

Development milestone: M39 — Resume

## Capability

0.6.0a3 resumes a stale persisted workflow by continuing the **same WorkflowRun**.

Already-completed tasks are preserved and not re-executed.

Remaining tasks receive new TaskAttempts only when they actually execute.

## Added

- Runner.resume();
- WorkflowRuntime.resume_run();
- ResumeError;
- durable TaskRun output checkpoints;
- Memory and relational checkpoint persistence;
- Alembic revision 0002_task_output_checkpoints;
- RuntimeEventFactory starting_sequence support;
- reconciliation-to-runtime state application;
- ACC-RECOVERY-002 SQLite restart acceptance.

## Resume identity

```text
resume  → same WorkflowRun
rerun   → new WorkflowRun
replay  → new WorkflowRun + historical references
```

## Durable dependency outputs

Portable successful TaskResult outputs are checkpointed as JSON.

After restart, M39 restores them into RunContext.dependency_outputs.

Opaque/nonportable Python outputs are never silently pickled for recovery.

If a remaining task needs a missing checkpoint, resume fails explicitly.

## Reconciliation application

```text
CONFIRMED_SUCCEEDED → existing attempt/task SUCCEEDED
CONFIRMED_FAILED    → existing attempt/task FAILED + fail-fast
CONFIRMED_CANCELLED → cancellation of same run
STILL_RUNNING       → ResumeError
MANUAL_REQUIRED     → ResumeError
```

## Persistence

New migration:

```text
0002_task_output_checkpoints
```

RunManifest schema remains version 1.

Plugin API remains version 1.

## Event history

Resume continues the existing run-local RuntimeEvent sequence.

No new recovery event enum is introduced.

## Acceptance

The reference scenario proves that after a real SQLite close/reopen:

- the WorkflowRun ID is unchanged;
- a completed producer task is not re-executed;
- its durable output is restored;
- only pending downstream work executes;
- event sequence continues monotonically;
- the same WorkflowRun reaches SUCCEEDED.
