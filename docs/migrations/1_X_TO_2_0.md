# PyWorkflowKit 1.x → 2.0 Migration Guide

## Purpose

PyWorkflowKit 2.0 deliberately changes the canonical package-root contract. Migration is
explicit: 1.x behavior is preserved as compatibility evidence and through a dedicated
compatibility facade, but it is not silently mixed into the V2 root.

## Release boundary

```text
1.1.0
  historical 1.x root + DX line
        ↓
2.0.0rc1
  canonical V2 root freeze
        ↓
2.0.0
  same qualified V2 implementation, stable metadata
```

## Root API migration

A 1.x application that imported legacy root symbols should first make its dependency
explicit:

```python
import pyworkflowkit._compat.v1_root as v1
```

That facade is the migration boundary for historical 1.x root contracts.

New or migrated 2.0 code should import canonical V2 concepts from the root or their
semantic namespaces:

```python
from pyworkflowkit import (
    ExecutionPlan,
    RetryPolicy,
    TaskDefinition,
    TimeoutPolicy,
    WorkflowDefinition,
    WorkflowRuntime,
)
from pyworkflowkit.executors import InlineExecutor
from pyworkflowkit.persistence import InMemoryMetadataStore
```

Do not mix V1 and V2 domain objects implicitly. Use the explicit
`pyworkflowkit._compat.v1_to_v2` migration functions where a supported semantic mapping
exists.

## Authoring model

1.x task definitions centered on handler references and the historical runtime facade.

2.0 task definitions represent one workload boundary directly:

```text
WorkflowDefinition
  └── TaskDefinition
        └── workload boundary
```

Workflow construction remains non-executing. Execution happens only through the runtime.

## Planning and DAG

`ExecutionPlan` is public and deterministic in 2.0.

Graph implementation details remain internal. Applications should persist or exchange the
portable plan/definition contracts rather than depending on internal graph classes.

## Runtime identity

2.0 distinguishes:

```text
CorrelationId
WorkflowRunId
TaskRunId
TaskAttemptId
```

Do not reuse one identifier type as another, even when textual values happen to match.

Retries create new `TaskAttempt` identities. Recovery preserves the existing
`WorkflowRun` and reconciles uncertain external executions before rerun.

## Retry, timeout, and cancellation

2.0 separates retry and timeout policies:

```text
RetryPolicy
TimeoutPolicy
```

Timeout does not imply confirmed termination of an external workload. Cancellation also
preserves uncertainty until the executor/provider can confirm the outcome.

Do not convert an unknown external outcome directly into a blind retry.

## Persistence

The V2 persistence contract stores workflow runs, task runs, task attempts, external run
references, state transitions, runtime events, durable output checkpoints, and manifest
references.

The migration chain remains append-only through:

```text
0001_runtime_metadata
0002_task_output_checkpoints
0003_retry_eligible_at
0004_v2_runtime_metadata
0005_v2_task_output_checkpoints
```

Upgrade an existing database through the packaged migration runner. Do not rewrite or
renumber historical revisions.

## Serialization

2.0 wire contracts are versioned, strict, and non-executable.

Serialized payloads are data, not executable Python objects. Duplicate JSON keys,
non-finite numbers, unsupported contract versions, and unsafe executable reconstruction
remain rejected.

## Executors

The V2 runtime uses explicit executor capabilities.

Select executors by qualified contract rather than assuming every backend supports the
same timeout, cancellation, serialization, concurrency, or async semantics.

`InlineExecutor` is the core qualified executor. Thread, process, async, and subprocess
executors remain explicit strategies with declared capabilities.

## Plugins

V2 plugins require explicit activation and use the V2 plugin API/entry-point groups.

Do not rely on implicit discovery side effects. Registration validation must not execute
plugin workloads.

## PyIngestKit and PyTransformKit

Sibling frameworks remain optional.

PyWorkflowKit integration modules preserve opaque workload/resource references and do not
make PyIngestKit or PyTransformKit mandatory core dependencies.

Retry ownership must remain explicit:

```text
workflow/workload retry     → PyWorkflowKit
provider/internal retry     → sibling framework
```

Unknown external outcomes require reconciliation rather than retry multiplication.

## CLI and DX

The canonical short CLI remains `pwk`.

Historical `pyworkflow` and `pyworkflowkit` console names remain compatibility aliases.
For automation, prefer deterministic `--json` output.

## Recommended migration sequence

```text
1. Pin and qualify current 1.1 behavior.
2. Route legacy root imports through pyworkflowkit._compat.v1_root.
3. Replace legacy definitions with V2 authoring objects.
4. Adopt distinct run/task/attempt identities.
5. Move retry/timeout semantics to V2 policies.
6. Migrate persistence through packaged revisions.
7. Replace internal graph dependencies with ExecutionPlan.
8. Make executor capabilities explicit.
9. Move plugin discovery to explicit V2 activation.
10. Qualify sibling adapters and recovery paths.
11. Run the complete application test suite on Python 3.11–3.13.
12. Remove compatibility-facade usage only after semantic equivalence is proven.
```

## Unsupported shortcut

There is intentionally no supported rule equivalent to:

```text
replace package version
and assume every 1.x object is a V2 alias
```

Ambiguous mappings fail closed. Migration must preserve semantics, identity, retry
ownership, external-run evidence, and portable boundaries.
