# PyWorkflowKit 0.6.0

Release date: 2026-09-27

## Capability

PyWorkflowKit 0.6.0 adds durable recovery semantics to the embedded runtime while keeping
recovery conservative, evidence-driven, and explicitly bounded.

This release closes M37 through M40 on top of the hardened multi-executor runtime
qualified in 0.5.0.

## Highlights

- read-only stale-run and resume-eligibility assessment over persisted evidence;
- stable TaskRun idempotency metadata using `task_run_id`;
- provider-specific reconciliation through `ExternalRunVerifier`;
- conservative normalized reconciliation outcomes;
- same-`WorkflowRun` resume semantics;
- durable JSON-portable TaskRun output checkpoints;
- preservation of already-SUCCEEDED tasks during resume;
- monotonic continuation of the existing run-local event sequence;
- durable `TaskAttempt.retry_eligible_at` evidence;
- non-blocking retry coordination in `ConcurrentRunner`;
- crash-safe retry wait that can resume with Attempt N+1;
- Alembic migrations `0002_task_output_checkpoints` and `0003_retry_eligible_at`.

## Recovery model

The recovery chain is:

```text
persisted runtime evidence
        ↓
M37 RecoveryInspector
        ↓
M38 Reconciliation when ambiguity exists
        ↓
M39 same-run resume
        ↓
M40 durable retry-wait continuation
```

A stale threshold identifies a recovery candidate. It is not proof that a running
workload has stopped.

Ambiguous local or external work must be reconciled or rejected explicitly before
resume.

## Resume identity

```text
resume  -> same WorkflowRun
rerun   -> new WorkflowRun
replay  -> new WorkflowRun + historical references
```

Resume preserves completed tasks and restores only portable dependency outputs that were
durably checkpointed.

PyWorkflowKit does not silently pickle arbitrary Python outputs to make recovery appear
possible.

## Retry-wait contract

Retry waiting does not introduce a new TaskRun lifecycle state.

```text
TaskRun RUNNING
Attempt N FAILED
retry_eligible_at = T
```

In the concurrent runtime, local coordination uses a monotonic deadline so the
coordinator can continue dispatching unrelated READY work during backoff.

The persisted `retry_eligible_at` value is wall-clock evidence that survives process
restart and allows recovery to determine when Attempt N+1 may safely begin.

The sequential Runner retains blocking local sleep behavior but persists eligibility
before sleeping.

## Persistence

The stable migration chain is:

```text
0001_runtime_metadata
        ↓
0002_task_output_checkpoints
        ↓
0003_retry_eligible_at
```

SQLite and PostgreSQL are both qualified against the same migration head.

## Contract freeze

0.6.0 intentionally preserves:

- WorkflowRun, TaskRun, and TaskAttempt lifecycle enum sets;
- RuntimeEvent taxonomy;
- RunManifest schema version `1`;
- Plugin API version `1`;
- the intentionally small package-root public API;
- executor capability contracts;
- RetryPolicy and RetryEngine ownership of retry decisions;
- scheduler, distributed worker, IAM, and control-plane responsibilities outside the
  core;
- the rule that a PyIngestKit Job is atomic from the PyWorkflowKit perspective.

## Qualification

The 0.6.0 release gate requires:

- Ruff lint and format checks;
- strict mypy over `src`;
- pytest with branch coverage >= 90%;
- Python 3.11, 3.12, and 3.13 test matrices;
- the complete M37-M40 reference acceptance suite;
- transverse recovery-contract qualification;
- SQLite migration qualification through `0003_retry_eligible_at`;
- PostgreSQL migration qualification through `0003_retry_eligible_at`;
- wheel build and isolated installation smoke;
- exact package / public `__version__` / CLI version consistency at `0.6.0`;
- migration resources present in the installed wheel;
- Bandit;
- pip-audit;
- detect-secrets;
- Dependency Review integration.

## Known limitations

0.6.0 does not claim:

- exactly-once execution;
- automatic proof that a stale process is dead;
- heartbeats or leases;
- distributed coordinator ownership;
- global recovery polling;
- automatic provider discovery for reconciliation;
- reconstruction of opaque nonportable task outputs;
- operating-system sandboxing;
- scheduler ownership;
- RBAC/IAM;
- a web control plane.
